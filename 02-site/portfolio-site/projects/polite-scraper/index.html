Case study

The Polite Scraper

Turns three pages of messy HTML into 60 schema-validated JSON records without ever being rude to the server — and without losing good data when one page is broken.

StackC# · .NET 9 · HttpClient · Schema validation · On-disk cache · Exponential backoff
RoleSole engineer
When2026
SourceGitHub repository

The problem

Writing something that fetches 60 pages takes an afternoon. Writing one that a server operator would not want blocked is a different problem: it has to identify itself, pace itself, never retry an answer, and keep the records it already has when one page fails.

What I did & decided

  • Checked before collecting, and wrote the check down: what the site is, what robots.txt says, whether terms exist, whether any personal data is involved. A 404 on robots.txt means no rules were stated, not that anything goes — it removes a prohibition, not the obligation to behave.
  • Confined every network call to one class, PoliteHttpClient, so the rules are enforced in a single place instead of remembered at each call site.
  • Set an identifying User-Agent with a contact address, and made the program warn when it is unset. A scraper nobody can contact is an anonymous one.
  • 500 ms delay plus jitter: 60 requests in two seconds looks like an attack; spread over ~35 seconds it looks like a reader.
  • Retried only timeouts and 5xx, with exponential backoff. A 404 is never retried — it is an answer, not an accident.
  • Added an on-disk cache so repeated runs are byte-identical and cost the server nothing, and emitted a run report and an error file alongside the data.

What came of it

  • A cold run takes ~41 seconds, 22 of which is deliberate waiting. A second run finishes in under a second, entirely from cache.
  • A broken page produces an error record, not a lost dataset — partial failure stays partial.
  • Reruns are byte-identical, which makes the output diffable and the whole thing testable.
