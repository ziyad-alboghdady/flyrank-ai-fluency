Case study

University Management System

One domain served two ways — Razor views for staff, a REST API for everything else — without duplicating the data layer.

StackASP.NET Core MVC · Web API · EF Core · ASP.NET Identity · Repository pattern · DTOs · Pagination
RoleSole engineer
When2026
SourceGitHub repository

The problem

The same university data needed a UI for staff and a JSON API for other systems. The naive answer is two codebases that drift apart within a month. The real question was how much could be shared before the sharing itself became the problem.

What I did & decided

  • Shared one repository layer and one DbContext between MVC controllers and API controllers, so a query is written once and both surfaces inherit it.
  • Kept the shapes separate: ViewModels for Razor, DTOs for the API. Sharing the data access is cheap; sharing the response shape is how an API ends up leaking form state.
  • Put pagination on both surfaces from the start — ?pageNumber=1&pageSize=5 — because an unbounded student list is a production incident waiting for enrolment season.
  • Used ASP.NET Identity with role-based authorisation, with destructive operations (deleting a student) reserved to admins.
  • Handled student photo upload to wwwroot/StudentPictures rather than storing binaries in the database.

What came of it

  • Adding a field means one entity, one repository method, and two small shape changes — not two features.
  • List endpoints stay flat in response time as records grow.
  • The API is usable by something that is not my own UI, which is the only real test of whether it is an API.
